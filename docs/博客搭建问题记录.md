## 一、环境准备

### 1.1 沙箱终端无法启动

**现象**

所有命令都直接失败，报错：

```
Failed to create unified exec process: helper_unknown_error: setup refresh had errors
```

**原因**

Codex 的 Windows 沙箱组件初始化失败，与命令本身无关。

**解决**

改用需要审批的提权模式（escalated）执行命令，绕开沙箱。后续所有命令都需要用户逐次批准。

**影响**

连带导致 `node_repl`、`computer-use` 两个基于沙箱的工具也无法使用。

### 1.2 Git、Node、GitHub CLI 全都没装

**现象**

```
git : 无法将“git”项识别为 cmdlet、函数、脚本文件或可运行程序的名称
```

**解决**

- Git：下载官方安装包静默安装
- Node：下载 zip 便携版，解压到 `C:\Users\zhang\.local\node\`，加入用户 PATH
- GitHub CLI：未安装，改用 Git + 凭据管理器完成认证

---

### 1.3 winget 下载失败

**现象**

```
An unexpected error occurred while executing the command:
InternetOpenUrl() failed.
0x80072efd : unknown error
```

**原因**

winget 的下载引擎走 WinINet，在证书吊销检查不可达的网络环境下会直接失败（和 1.4 同源）。

**解决**

绕过 winget，用 `curl` 直接从 GitHub Releases 下载官方安装包，再静默安装。

---

### 1.4 curl 报证书吊销检查失败

**现象**

```
curl: (35) schannel: next InitializeSecurityContext failed:
CRYPT_E_REVOCATION_OFFLINE (0x80092013)
```

**原因**

Windows 的 schannel 默认会联网检查证书吊销状态，该服务器在当前网络下不可达。

**解决**

给所有 curl 请求加 `--ssl-no-revoke`：

```powershell
curl.exe --ssl-no-revoke -L -o 文件.exe 地址
```

---

### 1.5 PowerShell 禁止运行 pnpm 脚本

**现象**

```
无法加载文件 pnpm.ps1，因为在此系统上禁止运行脚本
```

**解决**

只对当前用户放行本地脚本：

```powershell
Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned
```

## 二、GitHub 连接问题

### 2.1 推送超时

**现象**

```
fatal: unable to access '...': Failed to connect to github.com:443
after 21118 ms: Could not connect to server
```

**解决**

给 Git 配置代理，但**只对 github.com 生效**，避免影响其他代码托管平台：

```powershell
git config --global http.https://github.com.proxy http://127.0.0.1:7892
```

---

### 2.2 走代理后 TLS 握手失败

**现象**

```
schannel: failed to receive handshake, SSL/TLS connection failed
```

**原因**

schannel 后端在代理环境下仍然会做证书吊销检查，导致握手中断。同时 OpenSSL 后端在该代理下也会报 `unexpected eof`。

**解决**

保持 schannel 后端，并关闭吊销检查：

```powershell
git config --global --unset http.sslBackend
git config --global http.schannelCheckRevoke false
```

---

### 2.3 远程仓库和本地历史无关联

**现象**

推送被拒（non-fast-forward）。远程仓库在网页上创建时自带了一条 `Initial commit`，与本地历史没有共同祖先。

**解决**

先抓取，再以本地内容为准合并：

```powershell
git fetch origin main
git merge --allow-unrelated-histories -X ours -m "合并远程初始提交" origin/main
```

`-X ours` 保证 README 等冲突文件保留博客版本。

---

### 2.4 推送需要账号授权

**现象**

首次 push 时提示需要凭据。

**解决**

Git Credential Manager 自动弹出 GitHub 登录窗口，在浏览器完成授权后凭据存入 Windows 凭据管理器，后续无需重复登录。

---

### 2.5 代理对所有网站都不通

**现象**

浏览器打不开 GitHub，但梯子显示"已开启"。

**诊断过程**

分别通过代理访问多个站点：

```
google.com      → TLS 握手失败
cloudflare.com  → TLS 握手失败
api.github.com  → TLS 握手失败
claude.ai       → TLS 握手失败
github.com      → TLS 握手失败
```

代理端口在监听、进程也活着，但对**所有网站**都握手失败。

**结论**

不是 GitHub 被墙，是**梯子本身的上游节点挂了**。

**解决**

完全退出梯子进程后重新启动；仍不行则更换节点或检查订阅是否到期。

**经验**

不要只看"端口是否在监听"。端口开着不等于代理可用，必须实际请求一个网站验证。

---

### 2.6 直连和代理时通时不通

**现象**

同一台机器，有时直连 GitHub 正常、代理失败；过几个小时反过来。

**解决**

在发布脚本里做**多方案自动重试**：

1. 按当前 Git 配置尝试
2. 失败则强制直连（用 `-c` 临时覆盖代理配置）
3. 再失败则强制走代理

每种方案重试 2 次，全部失败才报错。这样无论网络怎么变，双击一次基本都能成功。

## 三、从静态站迁移到 Astro + fuwari

### 3.1 站点路径配置错误会导致样式全丢

**背景**

GitHub Pages 的"项目站"地址是 `用户名.github.io/仓库名/`，不是根路径。

**解决**

`astro.config.mjs` 两行必须配对：

```js
site: "https://zhangruina070113.github.io",
base: "/hello-my-repository/",
```

只改一处会导致 CSS、图片、JS 全部 404。

---

### 3.2 npm 依赖下载持续失败

**现象**

```
WARN GET https://registry.npmjs.org/... error (ECONNRESET)
FetchError: request to ... failed, reason: Client network socket disconnected
```

**原因**

官方 npm 源走代理不稳定，1109 个依赖包中大量连接被重置。

**解决**

改用国内镜像（这是下载 npm 包，和访问 GitHub 是两回事）：

```powershell
npm config set registry https://registry.npmmirror.com/
npm config delete proxy
npm config delete https-proxy
```

---

### 3.3 Pages 的发布来源需要切换

**背景**

站点最初用「Deploy from a branch」（分支部署），改用 Actions 后部署会失败。

**解决**

通过 API 把 `build_type` 改成 `workflow`：

```
PUT /repos/{owner}/{repo}/pages
{ "build_type": "workflow" }
```

### 3.4 自动部署流程

`.github/workflows/deploy.yml` 的关键步骤：

```yaml
- checkout
```

权限需要 `pages: write` 和 `id-token: write`。

## 四、写作工具的问题

### 4.1 中文批处理脚本编码错乱

**现象**

双击 `.bat` 后，中文提示变成乱码，甚至部分中文被当成命令执行：

```
'��消。' is not recognized as an internal or external command
```

**原因**

cmd 按系统代码页（GBK）解析 bat 文件，而文件是 UTF-8。即使加了 `chcp 65001`，解析顺序和文件编码仍会打架。

**更严重的问题**

用 bat 的 `echo` 生成 Markdown，文件会写成 GBK 编码，Astro 读取后中文全部乱码。

**解决**

放弃用 bat 生成内容。改为：

- `.bat` 只做启动器（纯 ASCII 内容，无编码问题）
- 实际逻辑用 Node 脚本（`.cjs`），文件读写统一 UTF-8

---

### 4.2 工具脚本无法使用 require

**现象**

```
ReferenceError: require is not defined in ES module scope
```

**原因**

项目 `package.json` 里有 `"type": "module"`，所有 `.js` 都被当作 ES Module。

**解决**

把工具脚本后缀改成 `.cjs`，强制按 CommonJS 解析，`require` 和 `__dirname` 都能正常使用。

---

### 4.3 发布脚本在失败后无法重试（真实 bug）

**现象**

第一次双击发布：提交成功，但上传失败。
第二次双击：提示「没有发现新改动，不需要发布」，实际内容还卡在本地没上传。

**原因**

脚本只检查了「暂存区有没有改动」，没有检查「本地有没有尚未推送的提交」。上传失败后工作区是干净的，于是被误判为"无事可做"。

**解决**

增加对未推送提交的检测：

```js
const upstream = git(["rev-parse", "--abbrev-ref", "--symbolic-full-name", "@{u}"]);
const ahead = git(["rev-list", "--count", upstream + "..HEAD"]);
```

只要 `ahead > 0`，即使没有新改动也继续上传。

## 五、Markdown 使用问题

### 5.1 换行和空格没有显示（最典型）

**现象**

在记事本里写了十几行笔记，发布后全部挤成一大段。

**原因（三条规则）**

1. **单个换行等于空格**。Markdown 只有遇到空行才分段
2. **行首 4 个空格会被当成代码块**
3. **连续多个空格会被压缩成一个**

**解决**

| 想要的效果 | 写法 |
|-----------|------|
| 分成两段 | 两段之间**空一行** |
| 插入代码 | 用三个反引号包起来 |
| 段落内强制换行 | 行尾打两个空格再回车 |
| 小标题 | 行首写 `##` 再空一格 |

**代码块示例**

````
```c
#define MAXSIZE 100
typedef struct {
    ElemType *elem;
    int length;
} SqList;
```
````

---

### 5.2 模板占位文字被发布出去

**现象**

文章正文里出现「在这里写正文，支持 Markdown 语法。」这句话。

**原因**

新建脚本生成的模板里带有示例文字，没有删除就直接发布。

**解决**

- 把写作提示改到 HTML 注释里（`<!-- -->`），不会显示在网页上
- 模板正文改成明确的示例段落，提醒用户替换

---

### 5.3 根本解法：所见即所得编辑器

问题的本质是「看不见渲染结果」。最终引入 **horseMD**（免费的 Typora 平替）：

- 打开文件夹 `E:\blog\src\content\posts` 作为工作区
- 编辑时实时渲染，所见即所得
- `Ctrl + /` 可切到源码模式对照学习语法
- 原文保真保存，不会擅自改动格式

## 七、网络排查经验

### 7.1 GitHub 资源下载的镜像方案

当 `github.com` 直连和代理都失败时，可以用加速前缀：

```
https://ghfast.top/https://github.com/用户/仓库/releases/download/...
https://gh-proxy.com/https://github.com/...
https://ghproxy.net/https://github.com/...
```

注意 Gitee 镜像可能只同步了很旧的版本，不能完全替代。

### 7.2 分层诊断法

遇到"打不开"时，按层排查，不要直接下结论：

| 层 | 检查方法 |
|----|----------|
| DNS | `Resolve-DnsName github.com` |
| TCP | `TcpClient.ConnectAsync(host, 443)` |
| TLS | `curl --ssl-no-revoke https://...` |
| 代理 | 用同一代理访问 google / cloudflare 等对照站点 |
| 应用 | 检查 Git 配置、npm 配置、系统代理 |

### 7.3 代理≠可用

端口在监听只说明进程活着。判断代理是否真的能用，必须用一个外部站点实测。如果代理对**所有站点**都失败，问题在梯子，不在目标网站。

---

## 八、经验总结

1. **先分清现象和根因**。"GitHub 打不开"可能和 GitHub 无关，是代理挂了。
2. **网络问题要分层**。DNS、TCP、TLS、代理、应用配置，逐层排除。
3. **编码是中文 Windows 的高发区**。批处理 + 中文 + UTF-8 的组合极易出错，能用脚本语言就用脚本语言。
4. **自动化要考虑失败路径**。上传可能失败、网络可能切换，脚本要能重试和回退。
5. **工具要贴合使用习惯**。用户要的是"双击就能写、双击就能发"，而不是记命令。
6. **看不见结果就会出错**。Markdown 的格式问题，最好的解法是所见即所得编辑器。
